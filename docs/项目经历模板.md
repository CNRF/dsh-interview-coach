# 项目经历模板

> 这个模板不是给 HR 看的简历模板，而是给**面试 AI 和面试官**看的"可追问素材"。
> 本插件会从你选的参考文件夹里自动提取项目清单、技术决策点和量化成果，
> 生成场景题、简历押题和追问。写得越有"决策 + 细节 + 数据"，生成的题目就越贴近真实面试。

---

## 一、先说结论：什么样的项目经历最"好用"

| 好用的写法 | 不好用的写法 |
|---|---|
| 写清**为什么做**这个决策（选型动机、方案对比） | 只写「使用了 Spring Cloud、Redis、RocketMQ」 |
| 写清**你做了什么**（负责哪个模块/主导哪个改造） | 笼统写「参与项目开发」 |
| 写清**效果如何**（前后对比、量化数据） | 「提升了性能」「优化了系统」这类形容词 |
| 写清**踩过什么坑**（回滚、故障、一致性） | 只写成功路径，没有任何边界情况 |
| 一个项目控制在 300–600 字，分点写 | 大段流水账，3000 字看不出重点 |

## 二、单个项目的模板

````markdown
## 项目名称（公司 · 时间范围）

**一句话定位**：这个系统是做什么的、服务谁、规模多大。

**业务规模**：用户数 / 订单量 / 日活 / 数据量 / QPS 峰值（有数字就写数字，没有写量级）。

**技术架构**：Spring Boot / Dubbo / MySQL / Redis / RocketMQ / K8s …（只列真正用到的）

**我的角色**：主导 / 负责 XX 模块 / 参与 XX 改造（人数和分工也写上，比如"3 人小组我负责网关层"）。

### 关键改造与决策

**1. 改造点：单体拆微服务（举例）**
- 背景：什么问题逼着我们必须拆？（发布耦合、单点故障、团队规模）
- 方案对比：为什么不继续优化单体？可选方案有哪些，为什么选这套？
- 拆分边界：按什么维度拆（业务域 / DDD 限界上下文 / 读写分离）？拆完遇到什么新问题（分布式事务、链路追踪）？
- 落地结果：服务数量、发布频率、故障影响面、延迟 / QPS 变化（具体数字）

**2. 改造点：数据库分库分表（举例）**
- 背景：单表数据量、增长速率、慢查询情况
- 分片键与策略：为什么这么分？跨分片查询和聚合怎么解决？
- 迁移方案：双写？增量同步？灰度切流？出问题怎么回滚？
- 结果：单表行数、P99 延迟、写入 QPS（前后对比）

**3. 改造点：引入消息队列 / 缓存一致性（举例）**
- 为什么引入？解决了什么具体问题（削峰、解耦、限流）
- 一致性怎么保证：事务消息、幂等、重复消费、消息丢失兜底
- 出过什么线上问题？怎么定位和修复的？

### 量化成果（面试官最爱问这个）

- 改造前 A → 改造后 B（延迟 / QPS / 成本 / 故障率）
- 数据口径要能说清楚：是 P99 还是平均？是单机还是集群？压测还是线上真实流量？

### 我踩过的坑 / 可以深挖的细节

- 上线过程中出过什么问题？（回滚、数据不一致、灰度期间双写冲突）
- 哪些决策后来发现是错的？如果重做会怎么选？
- 这个项目里你最想被追问的点是什么？（提前准备，你越主动，面试官越会往这问）

### 关键词

微服务拆分、分布式事务、分库分表、缓存一致性、消息队列、可观测性（给 AI 提供出题线索）
````

## 三、填写示例（虚构，仅演示结构）

```markdown
## 订单中心重构（某电商公司 · 2023.03–2023.11）

**一句话定位**：支撑公司自营业务的订单系统，日订单 80 万，大促峰值 5000 QPS。

**我的角色**：主导订单服务拆分与分库分表，带 2 名同学。

**关键改造：订单表 1.5 亿行拆分 256 张分表**
- 背景：单表 1.5 亿行，核心查询 P99 3.2s，写入峰值 1200 QPS 即将打满。
- 方案对比：读写分离（治标）vs 分区表（运维重）vs 分库分表（选了 Sharding-JDBC，因为团队栈匹配）。
- 分片键：商户 ID + 月份复合分片，理由：90% 查询带商户维度，同时避免单商户数据倾斜。
- 迁移：双写 + binlog 增量校验 + 灰度切流，按商户 ID 哈希分批，出问题一键切回旧库。
- 结果：单表降到 200 万级，P99 3.2s → 80ms，写入峰值支持 8000 QPS。

**踩坑**：灰度期间双写延迟导致个别订单状态不同步，用对账任务补偿；后来把状态机改成最终一致。
```

## 四、给插件的"目录组织建议"

插件选择参考文件夹后，会按**文件名优先**识别简历/项目文件（含 `简历`、`resume`、`项目`、`project`、`经历` 的文件排在最前），并读取 `.md` / `.txt` 内容。建议：

```
我的资料/
├── 简历-后端.md              # ← 最重要，放根目录
├── 项目经历/
│   ├── 项目A-订单中心.md
│   ├── 项目B-支付网关.md
│   └── 项目C-数据平台.md
└── 面试笔记/                  # 可选，用来暴露薄弱点
```

- 写 **Markdown / 纯文本**，不要 PDF / Word（插件读不了）
- 单文件建议 300–600 字，太长会被摘要，太短没有细节
- 文件名带「简历 / 项目 / 经历」能让提取更准
- 不要放大段敏感信息（手机号、身份证、公司内部数据），插件会把这些内容发给所选模型

## 五、常见反例

| 反例 | 问题 |
|---|---|
| 「负责后端开发，使用 Spring Cloud 微服务架构」 | 没背景、没决策、没数据，只能生成泛泛的概念题 |
| 「通过优化使性能提升 10 倍」 | 只说结论不说怎么做的，追问一句就露馅 |
| 「主导公司技术架构升级」 | 没有具体改造点，AI 无法生成决策类场景题 |
| 把公司所有项目都堆在一个 3000 字文件里 | 摘要时细节丢失，项目清单可能提取不全 |
